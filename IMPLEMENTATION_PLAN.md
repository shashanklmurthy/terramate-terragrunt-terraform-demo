## 0. What this repo demonstrates (maps to the original requirements)

| # | Requirement | Where it lives |
|---|---|---|
| 1 | Modules vs. live, non-AWS/local | `modules/` (Terraform) + `live/` (Terragrunt), `random`+`local` providers |
| 2 | Layered module usage | `modules/artifact` composes the leaf module `modules/labels`; live tree is layered foundation → application → reporting |
| 3 | Terramate auto-runs dependents on a transitive change | `live/*` `dependency` blocks + `terramate run --changed --include-all-dependents` |
| 4 | `generate` + `path_relative_to_include()` | `root.hcl` generate blocks (provider/versions/backend/stack_meta), state key uses `path_relative_to_include()` |
| 5 | README | `README.md` |
| + | Operator manual | `OPERATOR_MANUAL.md` |

**The dependency chain (the centerpiece):**

```
foundation  ──outputs──▶  application  ──outputs──▶  reporting
   (layer 0)                (layer 1)                 (layer 2)
```

`reporting` depends on `application`, which depends on `foundation`. Change `foundation` and
Terramate will run `foundation → application → reporting`, in that order, and nothing else.

### 3.2 `root.hcl`  (Terragrunt root — demonstrates `generate` + `path_relative_to_include()`)

```hcl
# Terragrunt root configuration, included by every unit in live/.
# Demonstrates:
#   - generate blocks (provider.tf, versions.tf, backend.tf, stack_meta.tf)
#   - path_relative_to_include() driving both the state key AND generated file content
#   - a tag convention passed down to modules as inputs (local-provider analogue of AWS default_tags)

locals {
  # Convention tags, mirrored from the org's root.hcl pattern. With local/random providers there is no
  # provider-level default_tags, so we inject these into modules as inputs instead (see live/* inputs).
  default_tags = {
    "owner:team"          = "platform"
    "owner:team:email"    = "devops@example.com"
    "iac:name"            = "terraform+terragrunt+terramate"
    "managed:via:project" = "terramate-terragrunt-terraform-demo"
    "backup"              = "false"
  }
}

# --- Local backend, keyed by the unit's path relative to this root.hcl -----------------
# path_relative_to_include() => "live/foundation", "live/application", "live/reporting".
# State is written under <repo>/.local-state/<relative-path>/terraform.tfstate (gitignored).
remote_state {
  backend = "local"
  generate = {
    path      = "backend.tf"
    if_exists = "overwrite"
  }
  config = {
    path = "${get_repo_root()}/.local-state/${path_relative_to_include()}/terraform.tfstate"
  }
}

# --- Terraform required version + providers -------------------------------------------
generate "versions" {
  path      = "versions.tf"
  if_exists = "overwrite"
  contents  = <<EOF
terraform {
  required_version = ">= 1.5"
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = ">= 3.0"
    }
    local = {
      source  = "hashicorp/local"
      version = ">= 2.0"
    }
  }
}
EOF
}

# --- Provider configuration -----------------------------------------------------------
generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite"
  contents  = <<EOF
provider "random" {}
provider "local" {}
EOF
}

# --- Demonstration of path_relative_to_include() INSIDE generated content -------------
# Terragrunt evaluates the ${...} interpolation at parse time, so each unit gets a different value.
generate "stack_meta" {
  path      = "stack_meta.tf"
  if_exists = "overwrite"
  contents  = <<EOF
# Generated by Terragrunt. Value is unique per unit, derived from path_relative_to_include().
locals {
  terragrunt_relative_path = "${path_relative_to_include()}"
}

output "stack_path" {
  description = "Path of this unit relative to root.hcl, injected via a Terragrunt generate block."
  value       = local.terragrunt_relative_path
}
EOF
}

# Empty root inputs; units add their own.
inputs = {}
```

### 4.5 `modules/artifact/main.tf`

```hcl
# Layered module: composes the leaf `labels` module, then creates local resources.
# NOTE on the source path "../labels":
#   This resolves because the live units source the WHOLE modules/ directory via the Terragrunt
#   "//" subdir mechanism (source = ".../modules//artifact"), so modules/labels is copied alongside
#   modules/artifact into the Terragrunt cache. See the operator manual for details.

module "labels" {
  source = "../labels"

  project     = var.project
  environment = var.environment
  component   = var.component
  extra_tags  = var.extra_tags
}

resource "random_string" "token" {
  length  = 12
  special = false
  upper   = false

  # Re-roll the token whenever the identity changes, so dependents observe a new value.
  keepers = {
    id = module.labels.id
  }
}

resource "local_file" "artifact" {
  filename = "${var.output_dir}/${module.labels.id}.json"
  content = jsonencode({
    id       = module.labels.id
    tags     = module.labels.tags
    token    = random_string.token.result
    upstream = var.upstream
  })
}
```

### 4.6 `modules/artifact/outputs.tf`

output "summary" {

## 5. Live units (Terragrunt) — the dependency chain

> Each unit sets `terraform.source` to `${get_repo_root()}/modules//artifact`. The `//` is the
> go-getter subdir separator: Terragrunt copies everything **before** `//` (the whole `modules/`
> directory) into its cache and uses the subdir **after** `//` (`artifact`) as the Terraform root.
> That is what lets `modules/artifact` reference `../labels`.

### 5.1 `live/foundation/terragrunt.hcl`  (layer 0 — no dependencies)

```hcl
include "root" {
  path   = find_in_parent_folders("root.hcl")
  expose = true
}

terraform {
  source = "${get_repo_root()}/modules//artifact"
}

inputs = {
  project     = "demo"
  environment = "dev"
  component   = "foundation"
  output_dir  = "${get_repo_root()}/.artifacts"
  extra_tags  = include.root.locals.default_tags

  # foundation seeds the chain; no upstream.
  upstream = {}
}
```

### 5.2 `live/application/terragrunt.hcl`  (layer 1 — depends on foundation)

```hcl
include "root" {
  path   = find_in_parent_folders("root.hcl")
  expose = true
}

terraform {
  source = "${get_repo_root()}/modules//artifact"
}

# DATA dependency on foundation. This is what Terramate parses to (a) order runs and
# (b) treat application as a dependent of foundation for --include-all-dependents.
dependency "foundation" {
  config_path = "../foundation"

  # Allow plan/validate to run before foundation has been applied (no real state yet).
  mock_outputs_allowed_terraform_commands = ["init", "validate", "plan", "fmt", "show", "output"]
  mock_outputs = {
    id            = "mock-foundation-id"
    token         = "mock-foundation-token"
    tags          = {}
    artifact_path = "/tmp/mock-foundation.json"
    summary = {
      id            = "mock-foundation-id"
      token         = "mock-foundation-token"
      artifact_path = "/tmp/mock-foundation.json"
    }
  }
}

inputs = {
  project     = "demo"
  environment = "dev"
  component   = "application"
  output_dir  = "${get_repo_root()}/.artifacts"
  extra_tags  = include.root.locals.default_tags

  # Consume foundation's outputs — this is the real data flow.
  upstream = {
    foundation = dependency.foundation.outputs.summary
  }
}
```

### 5.3 `live/reporting/terragrunt.hcl`  (layer 2 — depends on application, transitive on foundation)

## 6. Note on Terraform vs OpenTofu

The repo is Terraform-first. To run with OpenTofu instead, tell Terragrunt to use the `tofu` binary —
either set `terraform_binary = "tofu"` in `root.hcl`'s `terraform {}` block override, or export
`TG_TF_PATH=tofu` (older Terragrunt: `TERRAGRUNT_TFPATH=tofu`) before running Terramate. Nothing else changes.

### 7.3 Expected generated stacks (verify only — do not hand-edit)

`live/foundation/stack.tm.hcl` — no `after` (it's the root of the chain):

```hcl
stack {
  name        = "foundation"
  description = "foundation"
  id          = "<uuid>"
}
```

`live/application/stack.tm.hcl` — runs **after** foundation:

```hcl
stack {
  name        = "application"
  description = "application"
  id          = "<uuid>"
  after       = ["/live/foundation"]
}
```

`live/reporting/stack.tm.hcl` — runs **after** application:

```hcl
stack {
  name        = "reporting"
  description = "reporting"
  id          = "<uuid>"
  after       = ["/live/application"]
}
```

> If any `after` list contains the repo root or a parent path, the layout got nested by accident — fix
> the directory structure (units must be siblings) and re-run `create --all-terragrunt`.

### 7.4 First full apply (establishes real state so dependency outputs resolve)

```bash
terramate run -- terragrunt init
terramate run -- terragrunt apply -auto-approve
```

`terramate run` walks stacks in dependency order, so foundation applies first, then application
(reading foundation's real outputs), then reporting. After this you'll see three files under
`.artifacts/` and three state dirs under `.local-state/live/<unit>/`.

## 8. ✅ Verification of requirement #3 (the transitive-rerun demo)

This is the proof the whole repo exists for. Run it and capture the output for the README.

```bash
# 0. clean baseline on main
git switch -c demo/change-foundation

# 1. List the deterministic run order (independent of changes)
terramate list --run-order
#   expected:
#   live/foundation
#   live/application
#   live/reporting

# 2. Make a change ONLY in foundation (e.g. flip an input value)
#    edit live/foundation/terragrunt.hcl: change component tag or add an extra_tag, then:
git add live/foundation/terragrunt.hcl
git commit -m "change: tweak foundation input"

# 3. What does plain change detection select?  (foundation, possibly application via TG propagation)
terramate list --changed

# 4. THE HEADLINE: include all (transitive) dependents, in run order
terramate list --changed --include-all-dependents --run-order
#   expected:
#   live/foundation
#   live/application
#   live/reporting

# 5. Actually run them — foundation, then application, then reporting:
terramate run --changed --include-all-dependents -- terragrunt apply -auto-approve
```

**Why this works:** `--changed` selects `foundation` (its file changed). `--include-all-dependents`
adds every stack whose Terragrunt `dependency` graph points back to a changed stack — `application`
(direct) and `reporting` (transitive). Terramate then executes them respecting the `after` ordering
from §7.3. A change isolated to `application` would select `application` + `reporting` only, leaving
`foundation` untouched — verify that as a second case.

> **CI variant:** in automation, compare against the merge base instead of local commits:
> `terramate run --changed --git-change-base "origin/main" --include-all-dependents -- terragrunt apply -auto-approve`

### 9.2 `.github/workflows/_terramate-orchestrate.yml`  (reusable)

```yaml
name: _terramate-orchestrate
on:
  workflow_call:
    inputs:
      command:
        description: "terragrunt subcommand to run (plan|apply)"
        required: true
        type: string
      changed_only:
        description: "limit to changed stacks + their dependents"
        required: false
        default: true
        type: boolean
      git_change_base:
        description: "base ref for change detection"
        required: false
        default: "origin/main"
        type: string

jobs:
  orchestrate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4 # TODO(agent): pin SHA
        with:
          fetch-depth: 0

      - name: Install Terraform
        uses: hashicorp/setup-terraform@v3 # TODO(agent): pin SHA + version 1.11.4
        with:
          terraform_version: "1.11.4"
          terraform_wrapper: false

      - name: Install Terragrunt
        run: |
          TG_VERSION="0.77.22" # TODO(agent): keep in sync with .tool-versions
          curl -fsSL -o /usr/local/bin/terragrunt \
            "https://github.com/gruntwork-io/terragrunt/releases/download/v${TG_VERSION}/terragrunt_linux_amd64"
          chmod +x /usr/local/bin/terragrunt

      - name: Install Terramate
        uses: terramate-io/terramate-action@v2 # TODO(agent): confirm action name/version

      - name: Orchestrate
        run: |
          BASE_FLAG=""
          CHANGED_FLAG=""
          DEPENDENTS_FLAG=""
          if [ "${{ inputs.changed_only }}" = "true" ]; then
            CHANGED_FLAG="--changed"
            BASE_FLAG="--git-change-base ${{ inputs.git_change_base }}"
            DEPENDENTS_FLAG="--include-all-dependents"
          fi
          terramate run $CHANGED_FLAG $BASE_FLAG $DEPENDENTS_FLAG -- \
            terragrunt ${{ inputs.command }} -auto-approve -input=false
```

## 10. `README.md` (create with this content)

```markdown
# terramate-terragrunt-terraform-demo

A minimal, **fully local** (no cloud) reference showing **Terraform + Terragrunt + Terramate**
working together:

- **Terraform** defines reusable modules in `modules/`.
- **Terragrunt** defines the deployable "live" units in `live/`, wires them together with
  `dependency` blocks, and generates provider/backend/version files.
- **Terramate** orchestrates: it detects which units changed and runs them — plus everything that
  transitively depends on them — in the correct order.

Providers used: `hashicorp/random` and `hashicorp/local`. No credentials, no remote state.

## Architecture

\`\`\`
modules/labels    (leaf: naming + tags, no resources)
        ▲
        │ used by
        │
modules/artifact  (layered: labels + random_string + local_file)
        ▲
        │ sourced by every live unit
        │
live/foundation ──▶ live/application ──▶ live/reporting
   (layer 0)           (layer 1)            (layer 2)
\`\`\`

Each live unit produces a JSON artifact in `.artifacts/` and exposes a `summary` output. The next
layer consumes that summary through a Terragrunt `dependency` block.

## What each requirement maps to

- **Modules vs. live** — `modules/` (Terraform) vs `live/` (Terragrunt).
- **Layered modules** — `modules/artifact` composes `modules/labels`.
- **Transitive auto-run** — change `foundation`, and `application` + `reporting` re-run after it.
- **`generate` + `path_relative_to_include()`** — see `root.hcl`; the state key and a generated
  `stack_meta.tf` both derive from `path_relative_to_include()`.

## Quick start

\`\`\`bash
# one-time
terramate create --all-terragrunt        # import live units as stacks
terramate run -- terragrunt init
terramate run -- terragrunt apply -auto-approve

# see run order
terramate list --run-order

# change-driven, dependency-aware run (the headline feature)
terramate run --changed --include-all-dependents -- terragrunt apply -auto-approve
\`\`\`

See `OPERATOR_MANUAL.md` for how it all fits together and how to extend it.
```

```markdown
# Operator manual

## Mental model

Three tools, three jobs:

| Tool | Owns | Unit of work |
|------|------|--------------|
| Terraform | resource definitions | a *module* (`modules/*`) |
| Terragrunt | per-environment wiring, DRY config, dependencies | a *unit* (`live/*/terragrunt.hcl`) |
| Terramate | change detection + orchestration across units | a *stack* (`live/*/stack.tm.hcl`) |

A Terragrunt **unit** and a Terramate **stack** are the same directory: the `terragrunt.hcl` makes it
deployable, the `stack.tm.hcl` makes it orchestratable.

## How the layers connect (data flow)

1. `live/foundation` runs `modules/artifact` (component = foundation). It outputs `summary`.
2. `live/application` declares `dependency "foundation"` and feeds `dependency.foundation.outputs.summary`
   into its own `upstream` input.
3. `live/reporting` declares `dependency "application"` and feeds its summary in turn.

The `dependency` blocks do two things at once:
- **Runtime:** Terragrunt fetches the upstream unit's outputs (with `mock_outputs` covering plan-before-apply).
- **Orchestration:** Terramate parses them to set `after` ordering and to compute dependents.

## How change detection + ordering actually behave

- `terramate list` / `run` with `--changed` selects only stacks whose tracked files changed in git.
- **By default, dependents are NOT pulled in.** You opt in:
  - `--include-all-dependents` — add stacks that depend on the changed ones (direct **and** transitive).
  - `--include-direct-dependents` — only the immediate dependents.
  - `--only-all-dependents` — replace the selection with just the dependents.
- Dependency filters only follow **data** dependencies (Terragrunt `dependency` blocks / Terramate
  output sharing). They ignore ordering-only relationships (`stack.before/after`, `dependencies.paths`).
  That's why our units use real `dependency` blocks, not just ordering hints.
- Execution order always honors `after`, so a multi-stack run goes foundation → application → reporting.

Canonical change-driven command:

\`\`\`bash
terramate run --changed --include-all-dependents -- terragrunt apply -auto-approve
\`\`\`

In CI, add `--git-change-base origin/main` (PRs) or `HEAD^` (push to main).

### Fallback if your Terramate is too old for the flags

Upgrade is preferred. If you can't, force a stack to be considered changed with a trigger:

\`\`\`bash
terramate trigger live/application
terramate trigger live/reporting
terramate run --changed -- terragrunt apply -auto-approve
\`\`\`

## The `generate` blocks (in `root.hcl`)

Because each unit sets `terraform.source`, generated files land in the **Terragrunt cache** working
directory (not the unit dir):
- `versions.tf` — required Terraform version + `random`/`local` providers.
- `provider.tf` — empty provider blocks.
- `backend.tf` — local backend; state path = `<repo>/.local-state/<path_relative_to_include()>/terraform.tfstate`.
- `stack_meta.tf` — a generated `stack_path` output whose value is `path_relative_to_include()`,
  proving the function is evaluated per-unit at Terragrunt parse time.

Inspect what would be generated without applying:

\`\`\`bash
cd live/application
terragrunt init        # writes the generated files into .terragrunt-cache/...
find .terragrunt-cache -name '*.tf' | xargs -I{} sh -c 'echo "== {} =="; cat {}'
\`\`\`

## The `//` in `terraform.source` (important gotcha)

\`source = "${get_repo_root()}/modules//artifact"\`

The `//` is the go-getter "subdir" separator. Terragrunt copies everything **before** `//`
(the entire `modules/` dir) into its cache, then uses the subdir **after** `//` (`artifact`) as the
Terraform root. Without this, `modules/artifact`'s `module "labels" { source = "../labels" }` would
escape the copied tree and fail. If you ever split modules into their own repo, switch to a git source
like `git::https://.../modules.git//artifact?ref=v1.0.0`.

## Why artifacts and state are gitignored

Since Terramate v0.11, **untracked and uncommitted files count as changes**. If `local_file` wrote
artifacts into a tracked `live/*` directory, every stack would always look "changed" and the
change-detection demo would be meaningless. We write artifacts to `.artifacts/` and state to
`.local-state/`, both gitignored, so git diffs stay clean and change detection stays meaningful.

## Common commands

\`\`\`bash
terramate list                         # all stacks
terramate list --run-order             # in dependency order
terramate list --changed               # changed stacks only
terramate experimental run-graph       # visualize the graph
terramate run -- terragrunt plan       # plan everything, in order
terramate run --changed --include-all-dependents -- terragrunt apply -auto-approve
\`\`\`

## Troubleshooting

- **Cycle detected / unexpected `after`:** units got nested. Keep `live/*` flat and re-run
  `terramate create --all-terragrunt`.
- **`dependency ... has no outputs`:** the upstream unit was never applied. Run a full
  `terramate run -- terragrunt apply` once, or rely on `mock_outputs` for plan/validate.
- **Every stack always "changed":** something writes into a tracked dir. Check `.gitignore`.
- **Flag not recognized (`--include-all-dependents`):** Terramate is too old — upgrade.
- **Module file changes don't trigger stacks:** Terragrunt function-based `source` paths can hide
  module changes from detection. For module-change triggering, use a plain relative source path
  (`source = "../../modules/artifact"`) — at the cost of losing the `//` copy trick, so you'd then
  need labels reachable another way. For this demo (which triggers on *live-unit* changes) it's a non-issue.
\`\`\`
